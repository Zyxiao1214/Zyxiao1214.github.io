第一次读《重构》时，我把它当成一本技巧手册：提取函数、内联变量、搬移字段。
第二次读，注意力落在了前面那章"代码的坏味道"——它其实是一份体检报告，
而不是一张罪的清单。

## 坏味道是一种信号

重复代码、过长函数、过大的类，这些名字听起来像在指责写代码的人。
但作者的意思更接近：**这些地方以后改起来会疼**。

关键在于"以后"。代码本身能跑，坏味道不会让程序崩溃，
它侵蚀的是修改的速度和信心。

> 判断标准不是"这段代码好不好看"，而是"下一个人改它要花多久"。

## 我最常遇到的三种

### 1. 数据泥团

几个参数总是成组出现：

```ts
function createPost(title: string, slug: string, tags: string[], category: string) {
  // ...
}
```

当 `title` 和 `slug` 总是同时出现时，它们其实已经是一个概念了。
引入一个 `PostDraft` 类型，比继续加参数更容易维护。

### 2. 发散式变化

一个函数因为不同的原因被反复修改。比如格式化函数里同时处理日期、标签和作者名——
三种需求，三条修改理由。

拆开的依据不是"代码行数"，而是**变化的原因是否相同**。

### 3. 依恋情结

一个函数频繁访问另一个对象的数据，说明它放错了位置。
把它搬到数据那边，通常能同时消掉两处复杂度。

## 一个实用的判断流程

我把书里的思路简化成三个问题，改代码前先问一遍：

1. 这里如果有 bug，我要改几处？
2. 新增一个相似功能，是复制粘贴还是加参数？
3. 我要向别人解释它时，需要说几个"但是"？

第三个问题最有效。解释时"但是"越多，说明抽象越不干净。

## 重构和重写的区别

重构是在**行为不变**的前提下调整结构，每一步都可以跑测试验证。
重写是换掉行为边界，风险完全不在一个量级。

所以我的实践顺序是：

- 先把关键路径用测试固定住
- 每次只做一种小变换，跑一次测试
- 提交粒度尽量小，方便回滚

听起来很慢，但比"大改一次、debug 三天"快得多。

## 写在最后

这本书真正教我的不是技巧，而是一种态度：把代码当成会随时间老化的东西，
定期体检，小步调整。坏味道不是耻辱，是提醒。
